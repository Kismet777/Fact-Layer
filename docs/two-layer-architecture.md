# fact-layer 两层架构重构设计

> 状态：设计稿（整合多轮讨论，待拍板项见 §6）
> 日期：2026-08-18
> 目标读者：项目作者（nokismet），用于评审与后续实现
> 范围：把 FL 从「单一 slot 底座 + 三 tier」重构为「稳定事实层（文件管理）+ 动态事实层（slot 网）」两层架构，并明确认知层独立于 FL 之上。不涉及认知层的具体实现。

---

## 1. 需求：为什么要重构定位

### 1.1 三个结构性冲突

当前 FL 的病根是：**slot 和文档是「同一批事实的两种竞争表示」**，每条事实都要逐条纠结用哪种形态。这派生出三个冲突：

| 冲突 | 具体表现 |
| --- | --- |
| slot 管理 vs 文件内容管理 | 两种范式竞争，无统一规则 |
| 稳定事实存文档还是 slot | 稳定事实（架构、约定、技术栈）天生叙事，却被要求既能整篇读、又能单独查 |
| 动态事实存 slot 不合理但合适 | 动态事实（决策、进行中）短、高频、需单独寻址，却被迫套上稳定事实的重元数据 |

### 1.2 核心反转：决策是原因，事实是结果

FL 当前模型里，**事实是主体，决策是挂在旁边的普通类别**（`decisions.yaml` 里的 DEC-001、DEC-002……）。但真实因果方向是反的：

```
决策（原因） ──产生──▶ 稳定事实（结果）
```

每一条稳定事实之所以是今天这样，背后都有一串决策。FL 存了「结果」，却把「原因」降级成普通类别。这是当前定位最根本的偏差。

**git 类比**：FL 架构文档里写过「FL 很像 git」，但这句话没写完。git 的价值不在文件内容（working tree），而在 **commit 历史**——谁在何时、为何、拒绝了什么备选方案。FL 目前是「无状态、last-write-wins、无版本的快照底座」，建了 working tree，却漏掉了 git 真正值钱的 commit 历史。**而决策，就是 commit。**

## 2. 定位：两层架构

### 2.1 两层模型

把「原子承载操作，文档承载叙事」这条原则，从「每条事实单独判断」提升到「层的划分」。**层决定存储形态，不再有逐条判断。**

```
稳定事实层（文件管理）─── 结果 · 叙事 · 整篇读 · 缓慢变化
        ▲
        │ 着陆点（slot → 文件内具体位置）
        │
动态事实层（slot 网）─── 原因 · 决策 · 短 · 高频变化
```

| 维度 | 稳定事实层 | 动态事实层 |
| --- | --- | --- |
| 承载系统 | 文件管理 + 结构化骨架（schema + 索引） | slot 网 |
| 存储形态 | 文档（Markdown）+ 标准格式 + 逻辑索引 | slot（结构化，网状） |
| 本质 | 结果 / 叙事 | 原因 / 决策 / 演化 |
| 变更频率 | 低（90 天复核） | 高（7 天复核） |
| 权威性 | 内容权威，slot 网只是索引 | 决策权威，是变更的发起者 |

三个冲突由此消解：slot 和文件从「竞争」变「分工」；稳定事实永远是文档；动态事实永远是轻量 slot。

### 2.2 稳定事实层：文件管理 + 结构化骨架

稳定事实（架构、约定、技术栈、概览）**永远是文档**。它叙事、整篇读、长命，天生该是文档。「PostgreSQL 16」这种短原子只是文档里的小节，不再是独立 slot。

但 **git 全权管理文档不够**。git 系列操作只留**痕迹**（谁在何时改了什么），却无法提供**标准格式**和**逻辑索引**——它提升了可扩展性，却也提升了 agent 直接利用和建模的难度。

稳定事实层需要覆盖三个维度，git 只覆盖其一：

| 维度 | 载体 | 回答 | 谁提供 |
| --- | --- | --- | --- |
| 时间维 | git 历史 | 谁在何时改了什么 | git（已有） |
| 形状维 | 标准格式（schema） | 内容长什么样、怎么解析 | FL 定义 |
| 关系维 | 逻辑索引（index） | 有什么事实、在哪、什么关系 | FL 维护 |

- **标准格式**：稳定文档的统一结构约定（front-matter 字段、section 约定、锚点语法）。让 agent 靠「解析」约定格式，而非「理解」五花八门的 markdown 风格。
- **逻辑索引**：机器可读的稳定事实目录——`key → 文件锚点 → 状态 → 更新时间 → 关系`。agent 先读索引（轻量），不读全文，就知道「有什么、在哪、还准不准」。

**为什么 git 不够**：这正好对上 FL 自己的四属性。git 只服务**可溯源**（时间维），不服务**完整**（查得到，靠索引）和**一致**（关系网，靠索引里的依赖）。把稳定层全权交给 git，等于把「结构化」的责任推回给 agent 自己建模——这正是 FL 当初要解决的问题。

所以稳定事实层是**四件套**：

```
权威内容（文档 markdown）—— 叙事
标准格式（schema）       —— 形状，可解析
逻辑索引（index）        —— 发现，可导航
git 版本历史            —— 时间，溯源
```

**逻辑索引是两层之间的枢纽**：它既列「有哪些稳定事实」，也承载「动态 slot → 稳定锚点」的着陆关系（§3.1），还承载稳定事实之间的弱依赖。它不是动态层那种重依赖图，而是一层薄索引，承载发现与关系。

**标准格式与逻辑索引是同一套标注格式的两面**：标注格式定义的不是「内容怎么排版」，而是「文件结构怎么标注」——文件里有哪些部分、怎么寻址、什么关系、什么状态。内容文档用它标注自己的事实（front-matter / section / 锚点）；索引文件用它标注整个层的目录与关系（key → 锚点 → 状态 → 关系）。**索引文件本身也是这套标注格式的一种实例，不是另一套独立语法**。着陆点（§3.1）同样是这套标注格式的一种用途——它标注的是「动态层决策落到稳定层文件的哪个位置」。

### 2.3 动态事实层：slot 网

动态事实（决策、进行中）**永远是 slot**，但用轻量 slot。之前「不合理」是因为把稳定事实的重元数据（source / confidence / verified / reason）硬套在天天变的动态事实上；分层后动态层用适合自己的轻量形态，「短」的优势被完全吃下。

**动态层才是 FL 的「活」部分**：决策、进行中、依赖图、审计都在这。

## 3. slot 网设计

### 3.1 两条正交边

slot 不是表，是**网**。这张网有两条正交的边：

- **演化路径（时间轴）**：`slot → slot`，承载「决策是原因」。DEC-001 → DEC-002 → …，把历史变更进程串起来。追加式，不可删，只可 supersede。
- **着陆点（空间轴）**：`slot → 文件锚点`，承载「稳定=文档、动态=slot」。slot 锚定到文件内具体位置；查询入口是 slot 网，通过着陆点落到文件锚点，文件是权威内容，slot 网是索引。

### 3.2 slot 生命周期与颗粒度

slot 与 commit 是**两套时间线**，中间隔着「思考」到「动手」的逻辑间隔，不能混为一谈：

- **slot = 决策**：记录意识到的问题、做出的判断、暂缓的事项。
- **commit = 修改**：记录文件的实际变更。
- 关系是**引用**，不是**绑定**，且**多对多**。

```
空悬（open）      slot 记录「意识到但暂不解决」，无对应 commit
    │  决策被推进，促成文件修改
关联（linked）    slot 引用到 commit / 文件锚点（多对多）
    │  问题解决，决策落地
收敛（resolved）  slot 关闭，进入历史（可被 supersede）
```

**颗粒度不对齐是特性，不是缺陷**：

| 情况 | git commit | slot 网 |
| --- | --- | --- |
| 空悬 slot（暂缓的问题） | ❌ 完全看不到 | ✅ 记录「想到了但先搁置」 |
| 汇聚 commit（多决策成一行） | ✅ 看到改动，看不到决策来源 | ✅ 看到 commit 是哪些决策的汇合 |

空悬 slot 记录的是 git 历史里最稀缺的东西：**思考过、决定暂缓的痕迹**。

## 4. 借鉴 GitHub 的边界

### 4.1 借鉴 issue/tracker 层

借鉴的**不是 git 的 commit 机制**，而是 **GitHub 的 issue/tracker 层**——它本来就是独立于 commit 的决策追踪系统。

| GitHub 机制 | FL 对应 |
| --- | --- |
| issue（open 很久无人处理） | 空悬 slot（意识到但暂不解决） |
| PR 关联多个 issue（`Closes #123 #456`） | commit 汇聚多个 slot |
| issue 讨论线程 | slot 的 rationale / 演化讨论 |
| issue 的 open → close 生命周期 | slot 的空悬 → 关联 → 收敛 |

GitHub 的精髓：**issue 层与 commit 层分离，靠引用连接，而非绑定。** 这正是 FL 要借鉴的部分。

**不借鉴的**：

- 不把 slot 绑定到 commit（两者逻辑间隔，颗粒度不对齐）。
- 不直接使用 GitHub 平台——FL 的「可审计、可移植、不被锁定」价值观要求机制层用 git 协议，GitHub 只是可选的协作前端。

### 4.2 GitHub 的五个元假设盲区

GitHub 设计之初**从没想过服务 agent**。它「覆盖了我们的方案」恰恰证明我们和它共享了思维盲区。挖出它的五个元假设，才能挖出 FL 真正该补的地方：

| GitHub 元假设 | agent 时代要换成 | FL 的对应 |
| --- | --- | --- |
| 真相在文件里 | 真相在已校验的事实层 | 四属性（完整/当前/一致/可溯源） |
| 信任 = 人批准 | 信任 = 可验证 | 可溯源 |
| 决策是旁注 | 决策是一等公民 | slot 网 |
| close = 死亡 | 决策有生命周期 | superseded / 演化路径 |
| 消费者是人 | 消费者是 agent | 机机界面（MCP/导出） |

五个假设的根是最后一个：**GitHub 是一套「人机界面」，每个机制都默认消费者是「人」**。人能读自然语言所以 issue 用自然语言，人能凭直觉判断所以 review 靠人眼，人不会冷启动所以不需要「项目当前状态的一页纸」。agent 是另一种消费者：读自然语言会幻觉，每次都是冷启动，需要校验过的 ground truth。**GitHub 是人机界面，FL 是机机界面。**

## 5. 认知层（FL 之上）

个人分身 / 同事 skill 那层，本质是**蒸馏**——从决策 trace 里提炼出「这个人怎么想」。而 FL 最核心的纪律是：

> **核实，而非推理。从不合成没人声明过的新事实。**

蒸馏一个认知模型，恰恰是**推理 + 合成**。这越过了 FL 给自己画的那条线。

**结论：认知层是 FL 之上的独立系统，以 slot 网的决策 trace 为输入。** 它服务的是协作的另一个维度（人的思维模式），不是事实的四属性，所以不属于 FL，而是 FL 的消费者。

三层关系：

```
稳定事实层（文件管理）   结果 / 叙事
        ▲ 着陆点
动态事实层（slot 网）    原因 / 决策 / 演化
        ▲ 蒸馏
认知层（FL 之上，独立）  个人分身 / 同事 skill（概率性，带置信度）
```

## 6. 未决事项

### 6.1 待拍板

1. slot 的 `type` 分类：decision（决策）/ concern（意识到的问题）/ deferral（暂缓）——是否够用？
2. 空悬 slot 的过期/复核机制：长期空悬是否需要提示（类似 stale issue）？
3. 「着陆点」粒度：heading / 段落 / 显式锚点 ID（`<!-- anchor: layers -->`）？
4. slot 与 commit 的关联机制：git notes / commit trailer / 独立 `.facts/` 文件 + SHA 引用？
5. **统一标注格式（schema）的具体形态**：它是「文件结构标注格式」，统辖内容文档（front-matter / section / 锚点）与索引文件（key → 锚点 → 状态 → 关系）两类文件——两者共享同一套语法，索引文件本身也是这套格式的实例。是否复用现有 canonical YAML 模板的一部分？

### 6.2 可验证信任：认领到已有机制 + 真正剩余的缺口

「信任 = 可验证」不是一格空白——它就是 **需求树 §5「可自证」**（FL 证明自己四属性真的达成）；eval 设计稿 §0 已把 eval 定性为「证明四属性真的达成的元层」。初版说它「基本是空的」是低估：机制的**语法已想清、部分已建、部分待建**，只是**尚未在本文被认领**。拆成四个 facet：

| facet（可验证信任的一面） | 对应机制 | 现状 |
| --- | --- | --- |
| **供给准不准**（给定已知事实，重放校验对标 oracle） | eval-L3 **注入式演习 T3a** | spec 已写（`plans/2026-08-13-eval-l3-S2-t3a-impl-spec.md`）；实现暂缓入待办 |
| **被正确采纳**（FL 返回有没有真被用上） | eval-L3 **T2 观测** | 已实现并并入 main（`models/eval_results.py` / `core/eval_t2.py`） |
| **彼此一致** | `fl check`（结构/依赖）+ `fl audit`（语义）+ 写入端**冲突劝阻** | check/audit 已有；冲突劝阻见 `plans/2026-08-19-fl-input-admission-principle.md` |
| **未被污染**（值忠于源） | 源指纹 + **值失真对账** `_check_value_mismatch` / **FL-027 内外完整性对账** | 值失真对账半成品；FL-027 待实现 |

**可溯源（slot 有 source/verified）只是「可验证」的最初形态**；完整的机器可验证信任 = 上表四个 facet 各自闭环。所以真正剩余的不是「没有机制」，而是三件具体的事：①实现 T3a；②补污染检测（值失真对账 + FL-027）；③把这些散落的机制在本文正式接成「可验证信任层」。

**这仍是 agent 时代 GitHub 最给不了的东西**，但准确说，FL 不是「守住真相与决策、信任只是口号」——信任这层已有骨架（§5 可自证 / eval-L3），差的是补齐 T3a 与污染对账并把它们认领进来。
